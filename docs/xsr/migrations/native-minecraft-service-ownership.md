# Native Minecraft service ownership

This records the complete Minecraft boundary before changing its composition.
The existing native rule/classpath/asset exports remain compatible. The same
`nexa-minecraft` image will own instance discovery/library state, Java discovery and
acquisition, install planning/execution/recovery, launch preparation, JVM/process
lifetimes, output/crash analysis and instance-content management.

UI continues to emit typed intents and read state replicas. Numeric asynchronous
ports carry commands, queries, bounded output and immutable snapshots. No CLR
services, state stores, delegates, tasks, streams, process objects or exceptions
cross the boundary. Private launch identities remain privileged request values,
not public replicated state. Native owner dependencies must exclude presentation.

Foundation keeps canonical settings, tasks, logging and work ownership until the
Host composition is moved. Minecraft adapters consume explicit snapshots and send
asynchronous mutations/acquisitions to those owners. The existing account client
resolves launch identities, and downloads use the canonical host network client so
destination coalescing and scheduler budgets span callers. Platform world locks and
window notifications use owned handles/callback ports with physical retirement.

Managed development retains its existing public APIs and custom fixtures. Production
composition references the typed native client and contracts, rejects concrete
Minecraft implementation assemblies in the UI closure, and preserves route/DTO
admission identities. Shutdown cancels and drains processes, install operations,
file/world leases and callbacks before retiring the module context; images remain
loaded for process lifetime.

Acceptance requires actual independent AOT runtimes, preserved command/query routes,
discovery/install/launch/process parity, source-revision state, cancellation and
physical shutdown, canonical work/download ownership, dependency isolation, complete
launcher startup/closure and clean native-image reproducibility.

## Core service ports

The first implementation expands the existing image with version/instance discovery,
instance refresh, Java inventory, crash analysis, process start/cancel/output and
revision-preserving process/failure replicas. An independently compiled static client
references contracts only. Its 57-shape generated binary schema also encodes bounded
string maps for process environments. Known admission/I/O failures carry value
categories and parameter names; the caller reconstructs local exceptions.

The Linux AOT fixture uses real OS children through the private JVM Host transport.
It verifies manifest/instance identity, discovery refresh, Java inventory, crash
evidence, environment-map delivery, output channels and credential redaction, terminal
state revisions, local argument-failure reconstruction, cancellation and physical
child retirement during module close. The existing eight-engine AOT caller still
passes the original Minecraft algorithm ABI. The independent fixture is included in
the four-platform native workflow. Production route adoption and the complete
install/launch/management composition remain the next stage of this boundary.
The subsequent adoption adds awaited retirement for shared-cache producers after
canceled discovery, including flights detached from the logical cache by invalidation.

Core-port validation: warning-free Release build, 97-project architecture gate,
automatic coverage over 28 assemblies/14,964 executable bodies, and a clean native
rebuild with different Git/release metadata. The Minecraft image SHA-256 remains
`7045f6a422353d65e90e5a71a0c758ef00f0779ebad829e429b1f54b0972db1f`.

### Optional Java version components

Cross-platform CI discovered real Java installations represented by two- or
three-component System.Version values. The generated four-component constructor
rejected their omitted build/revision components (-1). The version codec keeps the
existing nullable/four-integer wire layout, validates component combinations and
chooses the matching two-, three- or four-component local constructor. Its schema
fingerprint changes so an outdated caller cannot silently decode a new owner.
The independent caller explicitly covers all three arities, null and malformed
negative/omitted components before inspecting any machine-specific Java runtimes.

## Canonical network delegation

Minecraft receives asynchronous reverse HTTP and download ports. Reuse the existing
64 KiB credited HTTP transfer machinery in both Minecraft peers, with Minecraft's
own protocol identity. The host adapter sends requests through its existing native
network client; it does not create a second download owner or budget. Download
descriptions return the host's committed transport policy and flow back through that
same canonical client's download admission. Default headers and timeout remain
properties of caller-local HttpClient adapters. Bodies and physical retirement stay
streamed and bounded; the buffered account HTTP helper is not suitable for large
Minecraft payloads.

The full production Minecraft owner will be published with `NexaNativeServices=true`
so its Common dependency uses the same descriptor-only download facade as the UI.
That facade accepts an explicit INativeDownloadPort and will be attached to the
Minecraft reverse adapter, which delegates to the host's existing network session. All native
Minecraft publishing/verification/reproducibility entrypoints must select this
composition consistently. Managed development keeps its original download engine.
No second download execution/cache implementation should remain reachable from the
production Minecraft owner.

## Host bridge foundation validation

The next implementation adds host HTTP/download delegation, task partitions and
immutable scalar settings snapshots. Production read routes use the native client;
the host lazily owns and asynchronously retires that session. The descriptor-only
download port is injectable without exchanging CLR services. Existing credited HTTP
code is linked under a Minecraft-specific identity rather than copied.

Validation at this stage: native-service UI build and default service-test build both
have zero warnings/errors; all 860 service tests pass. The independent AOT fixture
passes with the 82-shape schema
`22BBBE9B5B411F9348AE4DA3F81983E88801C7893D42DC4077783395A9B486CD`.
The full install/launch/management migration and actual production traffic through
the new host bridge remain required before declaring Minecraft ownership complete.

## Java acquisition ownership

The production Java installer now runs in the Minecraft owner. Its generated
asynchronous port carries component, absolute destination, optional reviewed-plan
fingerprint and bounded progress. The UI adapter implements the existing confirmed
installer contract; cancellation and close wait for the owner request and progress
worker to retire. The owner keeps durable install/recovery journals and task retry
actions. Task controls address the imported Minecraft partition in the canonical
host task collection.

Native Minecraft publishing, CI and reproducibility verification all select
`NexaNativeServices=true`. The owner attaches its descriptor-only download facade to
the reverse port and uses the host's existing native network session. Metadata
retains its two-minute timeout, and Java file acquisition retains ten minutes.
An independent NativeAOT caller installs a hash-verified file from a loopback server
through this full chain, checks imported terminal task state and owner-side history
dismissal, and closes Minecraft before retiring the host network dependency.

Manual preview/registration, complete launch and instance management still need
their remaining production routes moved before Minecraft ownership is complete.

Java acquisition validation: the independent NativeAOT caller passes the real
installation, canonical network/work admission, imported task cleanup, process
redaction/cancellation and physical shutdown cases with 83 generated DTO shapes
(`D88410677A41EACF99AC1F6912B3EE974C12B823392DBDC9C40A74C7E5971B87`).
The fixture uses an HTTPS manifest identity and an explicitly described loopback
transport; production journal URL checks remain intact. All 107 release-script
tests pass.

## Java inventory, manual acquisition and management

The next port set moves manual previews/receipts, license-confirmed acquisition,
registration management and bounded executable diagnostics into the Minecraft
owner. Foundation uses a caller-local Java locator that emits asynchronous native
queries; its synchronous invalidation only marks the next query for refresh.
Canonical settings retain registration persistence through asynchronous reverse
snapshot/conditional-write operations. Native inventory preserves stale-revision
errors and manual acquisition shares its task handle with the underlying installer,
so verification/registration adds no second task card. Public managed constructors
and synchronous registration stores remain available for managed composition.

Validation: 58 Java service tests pass, including delayed asynchronous registry
reads, stale inventory rejection and failed conditional persistence after verified
acquisition. The independent NativeAOT caller passes the 100-shape schema
`977DDB7A9311B8E2F2566829A611882751792C3A49BE467BF7C700481023266C`:

refusal without license confirmation, actual executable rejection, zero registry

Existing discovery/process cancellation and physical retirement cases also pass.
Production native-service UI compilation has zero warnings/errors, and the
architecture gate passes for all 97 projects.

## Remaining installation ports

The Minecraft owner will reference the complete Install implementation and own its
catalog, installation/modpack/recovery operations and task retries. Canonical host
settings provide asynchronous reads and transaction boundaries. All installer HTTP
clients must use the same host reverse port, including a distinct explicit
no-redirect policy for sources whose validation relies on inspecting redirects.
Caller-local HttpClient wrappers may share owned stream handlers without disposing
the handler when a per-operation wrapper closes. Preserve the Java-specific
timeouts and the existing general installer client timeout. Production route
adoption waits for rename/recovery settings transactions and the complete lifetime
to be wired; a native vanilla installation alone does not close this migration.

Installation-port validation: 20 related install/modpack tests pass, including
pause during an asynchronous policy read. Native owner/client and the independent
caller compile without warnings/errors. The actual NativeAOT fixture passes with
122 DTO shapes (`BA71C3B6D5ED70AEBFE3D71E4657B442775E2B044ABA05DAFCC62B225C531D6E`):
it fetches a SHA-1-pinned version document and asset index through host HTTP,
installs a hash-verified client through canonical native downloads, publishes the
instance and reads it back through native discovery. Existing Java/manual,
process cancellation and physical retirement cases continue to pass.
The native-service composition build is warning-free and the 97-project
architecture gate passes. An additional independent AOT case closes Minecraft
while installation is awaiting an asynchronous host policy query: shutdown first
pauses installation, drains that query, rejects late success and then closes the
remaining endpoint. Initialization/configuration admission closes before this
sequence. This preserves pause semantics before the generic request cancellation.

Instance recovery belongs to the same Minecraft owner: comparison, restore and
startup replay operate over its process state and await canonical host settings
capture/planning/commit/rollback. The owner references Management directly; its
static caller references only Management.Contracts. Production routing moves once
the shared work/process ownership required by this lifetime is present.

Launch account access is an asynchronous reverse port to the canonical account
owner. The Minecraft peer receives a privileged launch profile and resolved launch
identity as bounded binary values; neither enters renderer state. The caller-local
adapter retains account refresh/session ownership. The synchronous profile method
is unsupported in the remote adapter and is never implemented by waiting on IPC.

The full launch coordinator is composed in Minecraft with the existing Java,
process, file-completion and recovery implementations. Host reverse ports supply
account access, settings, resource admission, preflight evaluation and window
observations. Progress, Java acquisition and preflight prompts replicate typed
state with their source revisions. The UI sends decisions by numeric commands.
Module close cancels admission and waits for process/finalization work while host
callbacks remain available.

Native launch retirement also retains JVM observation/recovery tasks until process
exit and their final settings transactions complete. The owner closes incoming
commands before waiting for these finalizers; reverse host ports remain connected
until afterward. A visible-window probe invokes the caller-local taskbar callback
before returning its typed observation. Alternate-root Java scans use the same
asynchronous registration snapshot as the primary scan.

Production launch routing uses the native client after its asynchronous
configuration completes. The managed developer composition and its public service
APIs stay available in the managed build. Native production composition must not
construct a second launch coordinator, installer, process manager or Java registry.
Its instance source delegates to native discovery, while its progress and process
collections are replicas in the shared host store. Native configuration failures
are observed before desktop routes admit launch work.

The raw managed `MinecraftLaunchRequest` route is a developer-level API containing
JSON nodes. Production UI continues to submit instance/account identifiers through
`minecraft.start`; no raw manifest object is transported over the native boundary.
Launch diagnostics and post-exit finalization remain owned by Minecraft. Queries
cross as typed snapshots, and pending finalization is replicated so the desktop's
existing exit coordinator can await the owner without a synchronous remote read.

JVM observations, sampled run windows and inventory contexts also originate in
Minecraft and replicate into the host store. Resource-history estimation remains
canonical in the host: Minecraft submits a typed, validated observation sample
through an asynchronous reverse sink instead of constructing a second history.
Observation, context collection and recovery are all retained until retirement.

The independent native caller also dispatches the platform launch-hook worker
before composing its fixture. It links the two standalone OS supervisor sources from Platform.Runtime to
exercise the real command supervisor used by the production executable without
referencing that project and its metadata-service dependency. No Minecraft
service implementation enters the caller. Post-exit validation covers the actual
supervisor handshake and finalization-state retirement.

Native production launch must retain the existing preflight remediation actions.
Their domain algorithms belong to Minecraft.Launch; the managed composition keeps
its public binding facade and forwards to the same domain service. Native bindings
submit typed remediation requests to Minecraft. Java selection writes await a
canonical settings mutation port. Installation and launch bind the same owner-side
installer and completion instances before the production UI admits commands.
Native remediation composition exposes only the remote binding; managed-only
Java/install binding methods remain in the managed build. The production install
composer must not register a second local remediation owner. The native endpoint
also enforces the existing confirmation requirement before running domain work.
The remediation domain consumes an installation command interface from
Install.Contracts; Launch does not gain a dependency on the Install implementation.
The managed install service implements that existing command shape directly.
Primary-instance scope resolution and installed-loader projection move from the
aggregate composition project into Metadata, preserving the public scope type
through an assembly forwarder. Addon classification is a pure Install.Contracts
rule; the existing managed InstallCompatibility method forwards to it. This keeps
remediation independent of aggregate services and avoids an implementation cycle.
File repair uses the existing shared Recovery.Storage operation gate from Launch
so it remains mutually exclusive with restore/capture operations. Launch receives
an explicit reference and internal visibility to that gate; no second lock is
introduced for the native route.
Before requesting a game-window observation, Minecraft flushes pending process and
launch publications. The host's visible-window integration therefore reads the
matching process snapshot, including its requested title, before applying OS
window effects.

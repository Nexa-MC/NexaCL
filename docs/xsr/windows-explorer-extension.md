# Windows Explorer integration

ZIP installation commands are owned by a native C++ `IExplorerCommand` DLL. Explorer does not load the managed launcher, parse archives, contact providers, or wait for installation. A single selected filesystem ZIP enables the NexaCL flyout with modpack and theme children. Invocation starts the colocated launcher with an explicit mode and one quoted path; existing single-instance delivery handles an already running launcher.

The COM server is registered through a sparse identity package, using `windows.comServer` and `windows.fileExplorerContextMenus`. Its architecture matches Explorer (x64/ARM64). DLL paths and launcher paths are derived from the installed module, never the selected archive or current directory. The DLL exports only COM class creation and unload checks, and does not self-register in Explorer's process.

Production registration requires a trusted signed MSIX. Building an unsigned artifact is allowed for verification but must never be reported as successfully registered. Development registration is an explicit command and relies on Windows' existing developer-mode policy; neither the app nor installer enables developer mode or installs a trust certificate. Package registration is per user. All-user installation uses Active Setup to register for each user; uninstall removes only this package identity. Legacy ZIP menu and dedicated document associations remain available if modern registration fails.

Validation includes native COM enumeration, selection filtering, quoting, canonical command identities, reference counting, and package schema validation. Developer-machine registration and Explorer visual verification are separate from signed production-package acceptance.

`python eng/release/build_windows_shell.py --payload <publish-directory> --arch x64` builds the DLL, registration helper and sparse MSIX. Set `NEXA_WINDOWS_SIGNING_THUMBPRINT` to a code-signing certificate in the build user's Windows certificate store to sign and verify the outputs; its subject becomes the package publisher. No private key or password is copied into the payload. Normal registration uses `ShellIntegration/Nexa.ShellRegistration.exe --register`. `--development` explicitly registers the loose manifest on an already developer-enabled machine; it is never used by an installer. `--unregister` removes the current user's registration, while the elevated uninstaller uses `--unregister-all`.

Local evidence (2026-10-31): x64 native contracts passed, Windows SDK package creation passed, explicit developer registration succeeded, and an independent native process activated the registered COM surrogate and enumerated the flyout. The temporary test registration was removed afterward. No Explorer screenshot or signed production-package acceptance is claimed.

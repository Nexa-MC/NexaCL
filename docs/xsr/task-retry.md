# Failed acquisition retry and session downloads

Download/install/update owners register a retry callback with the task center. The callback receives a fresh reporting handle and cancellation token, and reruns the original command through the same validation and transaction boundary. The task keeps its identity, resets progress and steps, and admits only one retry. Retry is exposed only for failed tasks after the previous owner has disposed its handle (and therefore finished cleanup). Dismissal, retention eviction and shutdown release callbacks. Successful/canceled/paused work does not acquire a retry capability. Recovery retries use the existing journal rather than starting a conflicting transaction.
Before failing an attempt, its owner can lower the next attempt's cancellation capability using that attempt's token. A retained Minecraft publication retries through journal recovery, which keeps the established explicit exit pause/rollback flow and disallows generic task-card cancellation. Old attempt tokens cannot change a later attempt's policy.

The renderer reads `CanRetry` and emits the typed retry command; delegates and operation objects never enter published state or Sidecar messages. Retry and dismiss remain separate actions. Automatic launcher update already has its own failed/resume command and signed package journal; that boundary remains authoritative.

The shared download engine retains content-addressed downloads for the current host session when the caller supplies an authoritative SHA-1/SHA-256/SHA-512 digest and optional size. Cache bytes and partial transfers live outside transaction scratch directories so failed transaction cleanup cannot delete them. Every cache hit is rehashed before copying to a fresh destination; callers still perform their existing validation. Incomplete transfers can resume only when both the request and server support it. Bad digests discard the cached object and partial data. Unidentified downloads are never treated as reusable artifacts. Cache keys contain digests, never credentials or URLs.
Digest verification happens before committing each source attempt: a mismatched body is discarded and the engine advances to the next mirror/official source. Whole-file retry policy applies after this ordered source pass is exhausted.
Public download progress emits `Completed` once, after the requested destination has been materialized. Finishing the private cache object does not complete the caller's destination.

Cache storage is private to one host session. Host disposal prevents further cache work and deletes it once in-flight users release their leases. Existing durable install/Java/update recovery journals are preserved under their established shutdown contract; this session cache does not change their rollback or restart promises.

Coverage includes resource files, dependencies, mod/resource/shader updates, Minecraft and loader installation/editing, modpacks and updates, Java installation, and their resumable recovery tasks. Local imports that publish installation task cards also retain a retry path. Revalidation may reject a stale preview or modified destination; retry never silently approves a new destructive change.

Contract tests exercise duplicate clicks, owner cleanup, repeated failures, stale handles, cancellation, dismissal and shutdown; incomplete downloads resume into a different transaction directory, corrupt cache entries are rejected, concurrent identical artifacts share one transfer, and shutdown waits for cache users before removing storage. Integration tests retry real resource, Minecraft, pinned modpack and manual Java workflows (including Java verification and registration). Resource batch update fixtures verify one transfer can publish the same verified object to two targets. File retry policy fixtures use correct-length invalid digests to distinguish whole-file retry from truncated-source failover; concurrency fixtures use distinct artifact digests.

Desktop acceptance activates the rendered retry button and checks that the task card identity survives both retry and completion. `--validate-shell` also dispatches the retry intent, so the same route and callback lifecycle are exercised in native AOT and trimmed deployments.

Verification: Release solution build (zero warnings/errors), 787 service cases, 357 desktop cases and the 72-project architecture gate pass. Linux x64 NativeAOT and self-contained trimmed publications both pass `--validate-shell` and `--validate-setup`, including the retry route. The existing Jint IL2098 publication warning remains unchanged. Native migration previews pass in light/dark modes at both viewport widths (32 actual captures), preserving the rendered padding assertions and ready/confirmation/result states.
